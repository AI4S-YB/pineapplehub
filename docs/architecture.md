# 当前研究架构

本文面向开发者，记录整果侧面照片研究的目标、数据契约和验证边界。[Issue #21](https://github.com/AI4S-YB/pineapplehub/issues/21) 是学生采集与标注指南的唯一正文来源；仓库维护 [XML](annotation/label-studio.xml) 和正式配图，不维护学生指南镜像。

实验须支持具体程序功能：每个采集量都要说明由哪个输出消费、对应哪个实物或图像区域，以及如何比较预测与实测。下面分别记录已实现功能和研究方案；XML 使用橙色标签保存唯一中央主测果眼；自动识别、实例选择和相应测量程序仍需实现与验证。

## 0. 产品方向与原型经验

目标是供普通用户使用的 C 端 app，支持自然田间和采后照片。早期原型依赖纯黑试验台／黑布、俯视拍摄、硬币参照及传统图像处理；这些条件苛刻，果体和其他区域的误识别会使后续计算失败。引入机器学习的直接目的，是改善这些识别步骤及日常照片的适应性，同时保留有用的几何估计。旧拍摄条件不应重新成为学生的默认要求。

项目负责人报告：已对照过许多实物照片，前置识别正确时，现有近似所得结果与实测接近；明显失败多数来自果体等前置识别错误。这是已有使用经验，不应因参数不是标定值就判作巧合。现阶段保留它作为比较基线；本次公式审查没有重新计算这些实物样本，也未补造样本数或误差统计。推导、原始来源与适用边界见[裁剪圆柱近似审查](algorithms/cylindrical-approximation-review.md)。

## 1. 六项同等优先的输出

1. 果体长度：沿冠芽端至果柄端方向的直线长度，不含冠芽和果柄。
2. 整颗最大横径：垂直上述纵向的最大直线跨度，不是任意照片投影宽度。扁果可以宽大于长，不能按数值大小交换。
3. 体积：目标果体的体积，不含冠芽、果柄。
4. 宏观表面积：目标果体外表面积，排除冠芽、果柄，不逐一累计细小纹理凹凸。
5. 中央指定果眼长宽：输出指向唯一主测完整小果，同时显示其轮廓与尺寸。测量对象是相邻沟壑圈定的整枚小果外表区域，区别于花盘和中央凹陷。按 3.1 的位置规则选一枚；旧任务的第二枚实测原样保留。
6. 整果果眼总数：同一颗果实含背面的人工总数，不是可见实例数量。

六项均为核心目标。体积和表面积的独立参考测量方法、设备、样本与精度阈值仍待确定，本轮没有为学生新增缺乏可靠操作方法的字段。

| 程序功能 | 采集或参考数据 | 必须验证的对应关系 |
| --- | --- | --- |
| 果体长度、最大横径 | 可见果体轮廓、牌四角及实测边长、同状态果体实测 | 固定方向一致；单张投影宽度不能直接冒充整颗最大横径 |
| 体积、宏观表面积 | 轮廓及几何假设；另需独立体积／面积参考 | 对照独立实测，不能拿同一旋转体公式互证 |
| 中央指定果眼长宽 | 指定实例的轮廓、角色及该枚原始实测 | 必须比较同一枚、同一定义的尺寸，并在结果图中定位它 |
| 整果果眼总数 | 可见果眼实例、可见性、未知区域、含背面的人工整果计数 | 可见数与整果数分别报告；中央一枚的大小是否可外推需独立检验 |

牌只提供尺度与姿态约束，不是新增的最终产品输出；每项输出还须报告参考值覆盖率与预测可用比例。

## 2. 数据来源、身份与划分

学生负责一颗果实选定一张原照片、可见区域和可靠实测；开发端从 Label Studio 取得原文件，内部关联任务、区域、实测及来源。已有品种、批次、日期等信息尽量关联，不增加学生技术编号、外部对应表、照片配对或重复上传。实测必须对应拍照时的同一对象和状态，不能将后期成熟果尺寸回填早期照片。

同一实物的重拍、重复图、裁剪和增强保持在同一数据划分。开发端负责转换、划分、训练和评估，学生不选择训练／测试集。田间受叶片遮挡的缺测可能集中于特定阶段，不能假设缺测随机发生。

已有真实任务、标注和草稿，不能再按空项目处理。2026-10-19 已完成的配置切换改了两类果眼标签名称，并删除取消的 `target_fruit` 和 `reference_tag` 框结果；其他区域 ID、像素内容、图像尺寸、关联、已有数值、备注、状态和草稿身份均保留。

主测角色通过新增原生标签引入，只更新项目配置，保留全部任务、标注、草稿、预测和统计，不自动指定旧区域身份。切换前保留原始快照，在正式数据副本验证应用和恢复，正式写入前锁定记录并检查快照未变；有新增编辑先刷新验证。原图、备份及真实标注保持私有。

## 3. 标注与测量接口

橙色 `中央主测果眼（完整）`、绿色 `完整可见果眼` 和蓝色 `部分可见果眼` 都是可辨认的独立实例，后者只描述可见部分；每枚独立区域。紫色 `fruitlet_uncertain` 不是果眼实例，也不是明确背景。青色 `fruit_body` 汇集全部可确认可见果体，包括分离小块、阴影和贴合组织，保留一条记录；不补画遮挡，不包括冠芽叶片、果柄、背景和外翘细长尖端。

先果眼／紫色，最后青色；青色不会替代或合并已有区域。所需目标包围范围由完整青色掩膜生成，包括分离小块，裁剪余量由开发配置。这是训练／评估接口，不代表推理时自动定位已经实现。

| 字段 | 含义与级别 |
| --- | --- |
| `tag_side_mm` | 任务级，实物牌黑色正方形边长，不含外白边 |
| `fruit_length_mm` | 任务级，固定纵向果体长度 |
| `fruit_max_width_mm` | 任务级，整颗最大横径 |
| `total_fruitlet_count` | 任务级，人工整果总数 |
| `fruitlet_long_diameter_mm` | 区域级，所选完整果眼自身长径 |
| `fruitlet_short_diameter_mm` | 区域级，与该枚最长直线径垂直的卡尺跨度 |

所有字段可缺测，无默认值；尺寸正数、步长 0.1 毫米，计数正整数。现有每枚果眼的实测通过区域 ID 与其掩膜关联，已有两枚记录也保留各自原始值；主测角色由橙色标签保存，不从已有数值推断，也不将两枚数值汇总。空值不生成伪零，也不删除区域；清空一项不得影响其他字段或其他果眼。输入精度不是测量精度。[临时 Number 构建配方](../deploy/label-studio-number/README.md) 对应 1.23.2 的空字符串问题，产品跟踪见 [#22](https://github.com/AI4S-YB/pineapplehub/issues/22)，通用修复见 [上游 #9989](https://github.com/HumanSignal/label-studio/pull/9989)。原生 View 根据所选完整果眼显示区域字段；配置或镜像变更须验证保存、重开及导出。

数量级差异和极端值可提示复核，不能据统计自动改值或删除，也不能发现所有人共同填错单位。本轮不新增异常检测服务。标注完成状态不是测量有效性标签。

### 3.1 中央主测果眼与实例身份

“中央”是相对于果体和拍摄视角的位置，“主测”是本项目的测量角色；它们不是新的植物学器官类别。逐枚保存独立轮廓，为实例分割提供监督；唯一橙色实例直接给出人工选定的主测目标。这种标注形式不限定推理步骤。

主测选择的技术路线暂不锁定：可以在逐枚识别的同时学习选择分数，也可以直接定位或分割主测果眼；框、中心点等训练目标可由开发端从已有轮廓生成。位置规则也可作为候选方法，但没有项目实验支持它能在端侧小模型上可靠完成选择。人工选取规则不要求程序先恢复纵轴、识别冠芽端／果柄端或逐枚判断朝向；当前也没有这些中间量的独立标签。普通完整果眼的绿色标签表示完整可见且未被选为主测，不能直接当作“不适合测量”或“明显侧转”的监督。

现有轮廓、主测身份和对应实测，已提供主测识别、选择与尺寸评估所需的核心目标；数据量、标注一致性和模型准确率仍须分别验证。是否需要“整张照片没有合适主测对象”的样本，取决于训练方法和评估目标，不作为本轮采集的必备项目；没有橙色或提交复核也不能自动解释为无目标样本。

界面使用独立橙色的“中央主测果眼（完整）”，在现有 `fruitlets` 控件内区分它与普通完整果眼。该枚只保存一份掩膜和一个区域 ID；已画好的普通完整果眼可原位改标签，不重复涂一份。开发端把它还原为 `fruitlet` 实例、完整可见、主测角色三项含义，防止额外计数。复用 Label Studio 1.23.2 原生 `Label maxUsages="1"` 和 `perRegion` 控件；橙色最多一枚，橙色和绿色均显示原有测量字段。有效主测必须恰好一枚；无法确定的任务可零枚并提交复核。配置的数量限制不代替负责人检查位置和完整性。

主测对象固定为**一枚**：在果体纵向中部、朝向相机且完整可见的小果中，选择最靠近果体纵轴中点投影的一枚。中心落在沟壑上也只选最符合条件的一枚，不扩成两枚，不按大小或哪枚更容易对上程序结果选择。没有合适对象，或几枚之间无法可靠区分时，交负责人确认；不跳到边缘强凑。“强制一枚”规定有效主测记录的数量，不允许凭空补画对象或补造尺寸。候选范围和标注者一致性需用项目样本检验；“赤道”不自动等于果体最宽位置，现有代码用的是裁剪图半高。

当前不要求第二枚，也不计算两枚平均。已有两枚实测全部保留，不能为了新契约删除其中一枚或自动指定主测身份。以后若研究局部变异，另行定义取样角色与聚合规则；不改变本次唯一主测输出。

单枚方案服务于“定位并测量这一枚”的功能，不证明它足以代表整颗果实。现有代码恰好只取一枚，也不是取样充分性的证据。若用局部尺寸外推整果计数，须另外评估位置差异和外推误差，再决定是否需要多枚取样或不同的计数模型。

主测角色与是否测到数值分开：指定了对象但无法实测时，仍可保留角色和轮廓，数值留空。已有实测不能自动推出它就是唯一主测对象；升级时保留全部区域 ID、掩膜和数值，经复核确认角色。

尺寸定义也要统一。#21 现有“最长直线跨度及其垂直宽度”是此前写入的项目操作约定，不是 UPOV 或其他菠萝形态学指南的要求；不能反过来用 #21 为这项选择提供权威依据。[ImageJ 测量指南](https://imagej.net/ij/docs/guide/146-30.html#sub:Set-Measurements...) 将最大 Feret 径定义为边界两点间最大距离，可作为长径的几何定义来源。垂直方向的卡尺宽度也有通用图像测量定义，见 [Sympatec 的 FERETmax90](https://www.sympatec.com/en/particle-measurement/glossary/fundamentals-of-particle-characterisation/particle-shape)；这些资料均不规定菠萝中央取一枚。

程序目前使用最小面积外接矩形的两条边，与上述量不普遍相等。本项目现在明确采用最大 Feret 径及其正交卡尺跨度，即与长径平行的两接触面之间的距离；不采用最长垂直弦。不规则形状下两者可能不同。计算上可用已有轮廓几何方法实现，仍须将新计算与这一实测定义匹配并验证。不能仅将旧 `a_eq`、`b_eq` 字段改名；果眼长宽乘积用于整果计数的假设也须随定义重新核对。完整可见不代表该区域与牌共面或没有透视缩短。

### 3.2 图示必须符合实际操作

当前绘制操作是**按住鼠标左键拖动**，不是右键。Label Studio 1.23.2 的 [DrawingTool](https://github.com/HumanSignal/label-studio/blob/1.23.2/web/libs/editor/src/mixins/DrawingTool.js) 会过滤右键和中键；本项目已有左键绘制的浏览器操作记录。普通起笔、Ctrl 重叠起笔和松键图标均需与文字一致：绘制时标左键，松开时不把右键涂成按下状态。⑥配图已修正为左键着色，松开状态无按钮着色。

## 4. AprilTag 与物理边界

开发端复用现有 AprilTag 检测器取得编号和真实四角，学生不再画牌框、涂牌或点角。识别失败、多牌、目标对应不清交负责人。同编号可有不同打印尺寸，每张任务仍需对应实物牌的实测黑方边长，不从编号或 PDF 文件名推断。

当前 37 张原图曾用 AprilTag 3.4.5 检查，每张均有一个正确定位的 ID 0；这仅支持这些样本取消日常人工框，不证明无牌、多牌、遮挡场景的准确率。

牌在照片中放于果实侧边，不遮挡果体；在深度方向，牌面应尽量位于**通过果体纵轴、近似平行于成像面的平面**。侧视图中牌的截线应与纵轴的深度位置重合。仅把牌画得与纵轴平行，或放在相同高度，不能表达这一要求；②侧视图已将牌边缘与纵轴画在同一前后位置，并说明实物牌在果实侧边。“最宽处附近”用于帮助安排高度和邻近位置，不能代替深度对齐。

在正对相机、忽略畸变的平面近似下，像素跨度 `p = f_px × L / Z`。用牌推得的比例尺测量位于另一深度的对象，会得到 `L_est = L × Z_tag / Z_object`。因此牌与轴线深度接近有助于约束果体模型；牌前后错位会产生系统尺度误差。但朝向相机的果眼表面通常比纵轴更近，不能直接对所有果眼套用轴平面的比例尺。侧面轮廓还是曲面的切线投影，不自动等于同一深度的平面直径。

已知牌的物理尺寸和相机内参，可估计牌的姿态与距离；[AprilTag 官方姿态接口](https://github.com/AprilRobotics/apriltag#pose-estimation) 要求像素单位的 `fx`、`fy` 及主点 `cx`、`cy`。仅有 EXIF 焦距毫米数不足以直接代入，还须考虑传感器／有效图幅、缩放裁剪和畸变。单张牌不能独立确定未知曲面的深度或背面形状；果体几何模型及物理实测仍是必要的验证部分。

①②④中六处图案统一合成自 AprilRobotics 官方 AprilTag 36h11、ID 0 素材，与打印件的编码一致；反光与弯曲反例保留同一源图案。素材与修订提示词见[配图目录](annotation/illustrations/issue-21/)。最终图案的检测通过只能证明码可读，不能替代牌位置和尺寸语义检查。照片横向投影未必是整颗最大横径；不可见背面果眼、体积和表面积仍需额外假设及独立参考数据。

## 5. 当前代码与研究接口

当前 Rust／WebAssembly 应用仍运行硬币和切面方案：[scale_calibration.rs](../src/pipeline/scale_calibration.rs) 检测 1 元硬币；[roi_extraction.rs](../src/pipeline/roi_extraction.rs) 依纹理选择 ROI（目标图像范围）；[unwrap_metrics.rs](../src/pipeline/unwrap_metrics.rs) 使用圆柱重投影及旋转体轮廓积分估计几何。[fruitlet_counting.rs](../src/pipeline/fruitlet_counting.rs) 用阈值、形态学和连通区域选代表果眼，以有效面积与果眼面积关系估整果总数。[fast.rs](../src/pipeline/fast.rs) 是并行计算路径；测量修改需同步两条路径。

具体限制如下：

- [correction.rs](../src/correction.rs) 的 `unwrap()` 使用**扶正并裁剪后的果体 ROI 宽度**：竖向分支 `f = r = W_roi`，旋转 90° 的分支 `f = r = H_roi`。这是按目标尺度归一化的虚拟投影参数，不是原照片宽度，也不是恢复的真实焦距与果实半径。两条路径均先裁剪再调用；详细推导及源自 Stack Overflow 的公式见[审查记录](algorithms/cylindrical-approximation-review.md)。不应未经比较就把它替换成真实焦距或删除校正。
- 两条计算路径均在裁剪图半高附近筛选连通区域，以面积接近硬币面积的经验值及中心距离评分，只选**一枚**。这不等同于新方案中按固定位置指定主测对象；不能按预测结果挑最接近的人工实测来评估。
- 选中轮廓的最小面积外接矩形产生 `a_eq`、`b_eq`；整果数估计的分母是 `a_eq × b_eq`，并非真实曲面果眼面积。局部一枚能否代表整果平均占地面积，是需要人工总数验证的额外假设。
- 调试图会画出选中的框，但 [FruitletMetrics](../src/pipeline/mod.rs)、[历史记录](../src/history/model.rs) 和 [CSV](../src/export.rs) 没有保存该枚果眼的实例身份或原图轮廓。新功能必须让结果图、测量值和实例一起保留，才能复核“测的是哪一枚”。

[FruitletMetrics](../src/pipeline/mod.rs) 与 [CSV 导出](../src/export.rs) 已有长度、宽度、体积、代表果眼尺寸、表面积和总数字段，但其算法估计不是本次实测真值；旧 `major_length`／`minor_length` 命名也不能证明已符合新固定方向定义。[历史存储](../src/history/model.rs) 保留当前应用结果。本轮没有改变这些代码，没有实现 AprilTag 浏览器接入、训练数据转换器或 Burn 模型。

评估时先用人工掩膜隔离几何误差，再测自动识别引入的额外误差；这不要求等待几何研究全部完成才开发识别模型。优先 Rust、Burn 和社区已有实现，用必要的小适配器连接数据；训练配置、转换和评估应可复现。部署目标是用户端浏览器中的小模型，具体模型、输入分辨率、运行后端及设备预算尚未确定。大模型或人工能辨认的线索，不能据此认定端侧小模型也能可靠辨认；纵轴、朝向、完整性和主测选择均需在实际部署条件下验证。不新增独立整图合格分类器。旧 #20 的分类器、硬币和切面流程属于历史方案，不是新采集流程。论文分数、参数量、文件大小或原生设备速度均不能证明浏览器内存、延迟、量化精度或 Burn 兼容性；模型选择须另做项目数据及目标设备验证。

[旧英文算法](algorithms/algorithm.md)／[旧中文算法](algorithms/algorithm_zh.md) 的正文保留，仍用于理解当前代码，旧精度与鲁棒性论述不自动成为新研究结论。

## 6. 监督与验证顺序

局部紫色不自动使整张图所有用途失效，但当前训练代码尚未支持忽略未知区域。不能把紫色或未标注背景菠萝当作明确负样本。先复核，按具体训练目标简单排除无法可靠监督的样本或用途，保留原图及可用信息；不为抢救含糊标注建设复杂私有框架。

验证分两阶段：先用人工区域和可靠实测评估几何假设，区分尺度、投影、深度和形状假设误差；再加入自动分割，测其额外误差。六类指标分别报告误差、参考值覆盖率和预测可用比例，再报告同时可用比例，不以完成率代替准确率。按品种、成熟阶段、果形、田间／采后条件检查偏差和缺测分布。体积与宏观表面积需独立参考测量，不能用同一公式的两次计算互证准确；整果计数须对照含背面的人工总数。

中央果眼还要拆开验证三件事：指定人工实例时的尺寸误差；自动结果是否选中同一实例；完整自动流程的结果与可用率。预测实例与人工实例在同一原图坐标中匹配，身份不一致单独计为选取错误，不用数值碰巧接近掩盖。没有实测的实例仍可评价分割或选取，不能加入毫米误差统计；第二枚的数值不能替代被选中第一枚的真值。

## 7. 研究依据及适用范围

- [澳大利亚 PI17000 项目报告](https://www.horticulture.com.au/globalassets/laserfiche/assets/project-reports/pi17000/pi17000-final-report.pdf)：报告的每条螺旋果眼数用于育种性状评价，不等同整果总数，不能直接替换本项目参考值。
- [UPOV TG/295/1 菠萝指南](https://www.upov.int/edocs/tgdocs/en/tg295.pdf)（[WIPO 存档](https://tind.wipo.int/record/58225/files/tg295_en.pdf)）：第 36 性状将 eye 大小分小、中、大，第 37 性状描述小果顶端形态。这不能支持本项目“中央两枚、各量长短径”的取样规范，也不证明两枚能代表整体大小分布。
- [吴竞等，2022，菠萝果眼形成的组织形态学观察](https://www.ahs.ac.cn/CN/10.16420/j.issn.0513-353x.2020-1093)：研究花腔、花盘、宿萼及果眼深浅，包含成熟果中部果眼的深度分类。它有助于厘清测量对象，但不能把其中花盘宽度、凹陷深度直接当作本项目整枚小果外表区域的长宽。
- [Adje 等，2019，Morphological characterization of pineapple genetic resources from Benin](https://revues.cirad.fr/index.php/fruits/article/download/37310/37300/44449)，*Fruits* 74(4):167–179：把小果宽度列为种质评价性状，方法部分说明尺寸使用游标卡尺等工具。可核实的内容支持小果尺寸作为性状，但未提供本项目需要的“照片中央两枚、与实例一一对应”的取样依据。
- [Coppens d’Eeckenbrugge 与 Leal，2003，Morphology, Anatomy and Taxonomy](https://publications.cirad.fr/une_notice.php?dk=513593)，载 *The Pineapple: Botany, Production and Uses*，13–32 页：形态学专著来源。此次核实了作者机构的书目记录，未取得出版社完整章节用于逐项确认取样方法；不据书名声称它规定了中央一枚或两枚。可读的 [澳大利亚 OGTR 生物学资料](https://www.ogtr.gov.au/sites/default/files/files/2021-07/the_biology_of_pineapple.pdf) 第 3.2、4.3 节描述花发育为小果、小果融合形成复果及外表多边形单元，但不定义本项目的主测角色。

“果眼”在果皮外观、去皮加工和组织形态学中可能指不同边界；本项目必须配图明确采用整枚小果的可见外表区域。中央主测的数量与位置已选定为项目约定，其一致性及对整果外推的效果仍需验证，不能由器官的形态学定义推导。

这些来源没有给出本项目六项输出的准确性验收结果。体积／表面积参考协议、样本数量、精度阈值及最终模型选型仍是后续研究问题。
